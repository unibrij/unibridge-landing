Developer Integration

Integration Checklist

Checklist for selected partners during controlled UniBridge integration review.

1. Access and environment

  • Confirm approved integration environment.
  • Confirm API base URL.
  • Confirm /v2 API access.
  • Confirm available corridor scope.
  • Confirm test limits and supported assets.
  • Confirm whether partner webhooks are enabled.
  • Confirm whether HMAC signing is required.

2. Credentials

  • Receive partner ID from UniBridge.
  • Receive partner HMAC secret from UniBridge.
  • Store credentials securely.
  • Do not expose credentials in frontend code.
  • Do not commit credentials to source control.
  • Confirm credential rotation process.

3. Core flow

  • Call POST /v2/session/register.
  • Call POST /v2/session/resolve.
  • Call POST /v2/session/quote.
  • Call POST /v2/settlement/create.
  • Call POST /v2/funding/session.
  • Continue through provider checkout or approved funding instructions.

4. Funding confirmation

  • Confirm provider-handled funding is observed or confirmed.
  • Confirm funding amount, asset, and network match the selected route where visible.
  • Do not treat funding confirmation as final payout completion.

5. Settlement confirmation

  • Call POST /v2/settlement/confirm after provider-handled funding has been observed or confirmed, where enabled for the approved flow.
  • Confirm the response dispatches the settlement into funding_transform, execution, or an idempotent no-op.
  • Confirm settlement confirmation is treated as a dispatch step, not as final payout completion.
  • Do not retry settlement confirmation blindly if the resulting state is unclear.

6. Post-funding execution

  • Confirm UniBridge performs execution readiness checks after funding confirmation and settlement confirmation dispatch.
  • Confirm execution is submitted to the configured execution provider.
  • Confirm an execution provider reference is recorded where applicable.
  • Confirm provider status reconciliation runs after execution submission.
  • Confirm final status is updated based on provider outcome.

7. Status tracking

  • Call GET /v2/settlement/status?settlement_id=<id>.
  • Avoid excessive polling.
  • Treat intermediate statuses as non-final.
  • Treat funding_confirmed as non-final.
  • Treat submitted as non-final.
  • Treat processing as non-final.
  • Treat completed as final only when execution evidence supports it.

8. Go/no-go review

  • Corridor behavior has been validated.
  • Funding and execution evidence are available.
  • Settlement confirmation dispatch behavior has been tested.
  • Post-funding execution behavior has been tested.
  • Execution provider reference handling is understood.
  • Provider status reconciliation is understood.
  • Status tracking works through final outcome.
  • Error handling has been tested.
  • Manual review paths are understood.
  • Security requirements are satisfied.
  • Production use has been separately approved in writing.
